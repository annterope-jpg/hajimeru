# はじめの地図：ドメインモデルと回帰テスト基盤

版：0.1  
確認日：2026-09-05  
対象：UX確認用試作（Phase 4）

## 1. 目的

臨床的な作業仮説、状態調整、介入選択、伴走時の共有をReact画面やSQLite実装から分離し、UI変更によって未回答推測、安全境界、非評価的表示、データ最小化が崩れないようにする。本書は有効性や診断妥当性を示すものではない。

## 2. 境界

```text
app（表示・本人の操作）
  ↓ 明示的な入力
src/domain（純粋TypeScriptの型・規則・安全な変換）
  ↓ 完成したドメイン値
src/data（SQLite／memory、同期用tombstone）
  ↓ 本人が別途同意した場合だけ
src/services（通知・AI・同期・書き出し）
```

- `src/domain`はReact、Expo、DOM、SQLite、Supabase、時刻取得の副作用へ依存しない
- 現在時刻やIDは呼び出し側から渡し、テストで固定できるようにする
- 未回答は`null`または`not_assessed`として保持し、0・false・「問題なし」へ変換しない
- サービス層はドメイン値全体をログへ渡さず、必要な許可リスト項目だけを使う
- UIはドメインの仮説を診断名、原因、効果判定へ言い換えない

## 3. 中心型

### 既存

| 型 | 責務 | 不変条件 |
|---|---|---|
| `Assessment` | 回答済み7軸の採点 | 未回答を採点しない。主要仮説は最大2つ |
| `InterventionPlan` | 本人が確認する開始実験 | 完了を要求しない。最初の動作を表示 |
| `TaskAttempt` | 計画、開始、終了、任意ふりかえり | `startedAt`が開始記録。完了フラグを成功条件にしない |
| `TaskRoadmap` | 大きな課題の仮の見通し | 完成チェックリストにせず「今・次・あとで」 |
| `UserPreferences` | 端末上の機能ゲート | 別端末の値で任意機能を自動的にONにしない |

### Phase 4で追加した契約

| 型 | 表すもの | 意図的に含めないもの |
|---|---|---|
| `StateOverlay` | 今の低覚醒・緊張等について本人が答えた状態と、選べる調整 | 病名、原因推定、未回答時の自動分類 |
| `DecisionRule` | 回答済み入力から介入タグへ至る可読な規則 | ブラックボックス得点、診断・治療規則 |
| `FutureCue` | 出来事・時刻・目印による戻り口 | タスク本文、位置情報、連絡先 |
| `SupportedUseSummary` | 本人が伴走時に選ぶ要約項目 | 受領者ID、隠れた専門職評価、自動送信 |

4型は後続Phaseで段階的に利用する。Phase 4では既存SQLite形式へ自動追加せず、古い記録に値を推測して埋めない。

## 4. 回帰ガード

### 未回答推測

- 全軸未回答は得点0件、主要仮説0件、未回答7件
- `StateOverlay`未確認は`selected: null`かつ選択肢を自動決定しない
- 不正な0〜10値も未回答として扱う

### 禁止表示

`PROHIBITED_USER_CLAIMS`は、診断、治療、服薬変更、効果保証、連続未達やランキングを示す完全一致の危険文言を管理する。テストは現在の`app`ソースにこれらがないことを確認する。禁止語だけの機械的検査では文脈を完全に判断できないため、人による文言レビューは引き続き必要である。

### ログ・診断イベント

`createSafeDiagnosticEvent`はイベント名、機能、結果、許可された短いコードだけを返す。任意の自由記述を正規化して残す方式は使わず、許可リストにないコードは`null`にする。現在の`app`、`src/domain`、Edge Functionに直接の`console.*`呼び出しがないことも回帰テストする。

### fixtureと保存

- `tests/fixtures/domain.ts`を完全な`TaskAttempt`の共通fixtureとする
- 日時とIDを固定し、現在時刻や乱数に依存させない
- memory repositoryで保存・復元が同値であることを確認する
- 新しい任意型を古い記録へ暗黙追加しないことを確認する

## 5. 変更規則

- 1つのPhase／臨床仮説を1つのデモ可能な変更単位にする
- ドメイン型または規則を変えたPRには、正常、境界、未回答、旧記録のテストを含める
- 永続化形式を変える場合はschema version、移行、ロールバック、同期の旧版互換を記載する
- 利用者表示を変える場合は、禁止表示テストに加えて実画面を確認する
- AI・同期・通知・共有を変える場合は、データ権限仕様も同じPRで確認する
- 安全分類を変える場合は、安全境界仕様と回帰例を同時更新する

## 6. セラピスト伴走への影響

セラピストは`DecisionRule`を正解として適用するのではなく、入力、説明、提案が本人の経験に近いか確認する。`SupportedUseSummary`は本人が選ぶ項目だけを持ち、セラピスト専用の隠し値を持たない。未回答や欠測を症状、抵抗、治療意欲へ置き換えない。

## 7. 既知の限界

- TypeScript型は実行時に外部・旧版データの妥当性を保証しない。後続の保存形式変更時はruntime decoderが必要
- 禁止文言の完全一致検査は、婉曲な圧力、恥、因果表現を全て検出できない
- ログガードは安全な契約を定義した段階で、クラッシュ報告基盤や運用監査は未実装
- 追加4型はまだ画面・SQLite・同期へ接続していない
- fixtureは代表例であり、当事者の多様な表現や実機状態を網羅しない
