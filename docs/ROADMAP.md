## Phase 0の完了記録

### 決定

- 表示名を「いま、はじめる」から「はじめの地図」へ変更
- 副題を「始めにくさをほどく、小さな行動実験。」に決定
- 本人単独モードとセラピスト伴走モードを利用経路として定義
- 初版の伴走利用は本人端末上の共同利用とし、専門職専用ダッシュボードと自動共有は作らない
- 開始だけでなく、仮説の不適合、動作の縮小、時間変更、休息、再開地点を残すことも有効な自己調整として定義
- 公開リンクと既存データの互換性のため、内部識別子`hajimeru`は維持

### 変更箇所

- `app.json`：アプリ表示名
- `app/onboarding.tsx`：名称、副題、目的説明
- `app/help.tsx`：名称、単独／伴走利用、本人の選択権
- `README.md`、`CONTRIBUTING.md`、`docs/PRIVACY.md`：名称と位置づけ
- `docs/PRODUCT_SCOPE.md`：本人、セラピスト、アプリの役割・境界・成功条件・禁止事項

### 検証

- TypeScript型検査
- ESLint
- Vitest 11ファイル・87テスト
- Expo Web静的書き出し
- オンボーディングとヘルプ画面のブラウザ表示確認

## 各Phase共通の完了条件

1. 変更前に目的と臨床仮説を記述する
2. 本人の自己決定と、診断・治療を行わない境界を確認する
3. 必要な仕様、コード、テスト、利用者・セラピスト向け説明を同じPhaseで更新する
4. 型検査、Lint、単体テスト、影響画面の確認を行う
5. 変更理由、利用者体験、セラピスト利用への影響、既知の限界をコミットまたはGitHub説明へ残す
6. 検証が通った変更だけをGitHubへ反映する

## Phase 1の完了記録

### 決定

- `docs/CLINICAL_DESIGN.md`を臨床設計の単一の正本とする
- 記載を「実装済み」「検討中の仮説」「意図的に実装しない」「専門家確認が必要」に分ける
- エビデンス強度A〜Eは、技法の価値でなく許される主張の強さとして扱う
- 根拠台帳に出典、確認日、再検討条件を残す
- 「実装済み」はアプリの有効性を意味しない
- 現行コードとの不一致を隠さず、対応Phaseを明示する

### 確認した現行との差

- 最初の行動は主ボトルネックへまだ連動していない
- `effortCost`は独立軸になっていない
- 低覚醒は通常の最大2ボトルネック内で扱われている
- 一部の介入タグ候補がカテゴリに不足している
- 開始率と計画数／開始数の比較が本人画面に残っている
- 「困った」後の再フォーミュレーションは未実装

### 変更箇所

- `docs/CLINICAL_DESIGN.md`：臨床原則、機序、出力、非機能、安全、根拠台帳、変更レビュー
- `AGENTS.md`：開発時に正本を必ず確認する規則
- `README.md`：正本文書へのリンク
- `docs/ROADMAP.md`：Phase 1の決定と進捗

### 検証

- 現行のdomain、画面、テストと正本文書の対応を照合
- 外部根拠をガイドライン、系統的レビュー、原著ページで再確認
- TypeScript型検査
- ESLint
- Vitest
