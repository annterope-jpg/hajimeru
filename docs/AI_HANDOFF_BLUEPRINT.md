## 目的
この文書は、ChatGPT・Codex・ブラウザ側AI・Hermesなどが途中参加しても、現在地を誤認せず、1回の改定で1 Phaseだけを進められるようにするための入口です。

- 改定方式: 1回の改定で未完了Phaseを1つだけ扱い、仕様→実装→検証→説明→GitHub反映まで完了してから次へ進む。

- `main` はPhase 0〜14の累積実装をまだ取り込んでいない。Phase群は積み重ね型PRとして進行中。

## Claude相談から引き継いだ中核原則
1. 着手困難を一枚岩として扱わず、機序別に分ける。
   - taskClarity
   - aversion
   - rewardDistance
   - lowActivation
   - cueWeakness
   - competingReward
   - timeAmbiguity
   - effortCost は嫌悪と分けて扱う方向
2. 入力した内容は、最も目立つ出力へ反映する。アセスメントを儀式化しない。
3. 遅延嫌悪と遅延割引を混同しない。
4. 低覚醒・疲労・freezeを同一視しない。認知的方略の前に状態調整を検討する。
5. コンパッションは「優しい言葉」より構造で実装する。
   - 失敗率・達成率・ストリークを本人に見せない
   - 欠測や未開始を意欲不足として扱わない
   - 課題側の大きさ・摩擦へ帰属させる
6. 診断、治療効果、服薬効果、因果を断定しない。
7. ネガティブな未来帰結を想像させるEFTは使わない。EFTはポジティブ価で検討する。
8. AI・同期・通知・共有は別々の任意権限。拒否しても端末内機能を使えること。
9. 本人に見えない専門職評価、自動共有、治療遵守スコアは作らない。

## 毎回の作業手順
1. `AGENTS.md`、`docs/CLINICAL_DESIGN.md`、`docs/ROADMAP.md`、`docs/PRODUCT_SCOPE.md`、`docs/SAFETY_BOUNDARIES.md` を読む。
2. 直前Phaseのブランチ/PRとテスト状況を確認する。
3. 今回扱うPhaseを1つだけ決める。後続Phaseを先取りしない。
4. 変更前に目的、臨床仮説、禁止事項、想定リスクを書く。
5. 新しい `phase/<番号>-<短い名前>` ブランチを直前Phaseから作る。
6. 必要な仕様、コード、テスト、利用者説明、セラピスト説明を同じPhaseで更新する。
7. 少なくとも以下を実行する。
   - `pnpm typecheck`
   - `pnpm lint`
   - `pnpm test --run`
   - `pnpm export:web`
   - `git diff --check`
8. 実装結果、利用者体験、セラピスト利用への影響、既知の限界をPR本文に残す。
9. 失敗した検証を隠さない。テスト未実行は未実行と明記する。
10. 次Phaseの仕様を実装せず、`docs/ROADMAP.md` の進捗だけ更新する。

## GitHub反映の原則
- `main` に直接コミットしない。
- 1 Phase = 1ブランチ = 1PR を基本とする。
- Phase 0〜20は依存関係があるため、直前Phaseをbaseにした積み重ね型PRを維持する。
- 「GitHubへ反映」は、まずブランチ・コミット・PR・検証結果までを指す。
- `main` への自動マージは行わない。統合時はPhase 0〜20の依存関係、CI、差分、公開安全性をまとめて確認する。

## 重要な変更禁止点
- 開始率・達成率・完了率、ストリーク、未実施日を本人向け評価として表示しない。
- 欠測・拒否・保留を症状、抵抗、意欲不足として推測しない。
- AI・同期・通知・共有を勝手にONにしない。
- 診断名、重症度、服薬変更、治療効果をアプリが判定しない。
- 危機対応を通常の着手支援に埋め込まない。安全境界仕様を優先する。
- セラピスト専用の隠れた評価や本人同意のない自動共有を作らない。
- 臨床効果が未検証の設計仮説を、効果が証明された機能として表現しない。

## AI間の役割分担
